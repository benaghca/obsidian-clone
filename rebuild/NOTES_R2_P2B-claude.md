# NOTES_R2_P2B: link-index deltas

Built on `rebuild/r2-p2b-claude` from `b9fb338` (brief: `R2_P2B_TASK.md`), on top of merged P2a. This is the link half of RUST_PERF_PLAN §4.2 plus the reverse index of §4.6. Not done here: `vault-changed` carrying file entries, `changes_since` for tags and files, consumer patching (graph, Bases, Tags view), P3 (faster open), and the file tree.

## In plain words

- Before, a second after every save (and after every outside change), the page asked for the **whole** link index. Rust resolved every link of every note (24 ms at 20k notes, 74 ms at 50k), sent 3.1 MB / 7.9 MB, and the page parsed it (7.5 / 18 ms).
- Now Rust keeps every note's resolved links in memory and updates only the notes a change can affect. The page asks "what changed since version N" and gets only those notes, usually **55–300 bytes**, and patches its copy.
- The backlinks count and pane (`backlinks` for one note) read a reverse index instead of walking every note: 15 / 50 ms → **3–5 µs**.
- Nothing visible changes. The page's `vault.links` is identical to a full read, key order included, after every refresh. It is still a new object each refresh, and still refreshed at the same moments (1 s after a save, after each outside batch). Every consumer sees the same data at the same time as before.
- The cost: opening a vault builds the table once, so `scan` is about **11 % slower** (+40 ms at 20k, +110 ms at 50k), and memory is about **5 % higher** (+12 / +29 MB). The page's first link read after open gets 60 ms cheaper at 50k, so the Rust-side open total grows about 5 %. A folder rename also rebuilds the table once (see Measurements).

## How it works

**`src-tauri/src/index/link_table.rs` (new): `LinkTable`**, a field of `Index`.

- **Per note with links:** where each link points (`slots`, an index into its `outgoing` or `markdown` list), its `LinkEntry` (that note's part of `link_index`), and the name-map keys its resolution read (`reads`).
- **`by_target`:** target path → notes linking to it, sorted by path. `backlinks` reads only those notes, in the order the old full walk produced.
- **`readers`:** key → notes whose resolution read it. Keys are stored as a 64-bit FNV-1a hash of (map, key), not as strings. Two keys sharing a hash only make a change wake more notes than needed, never fewer. That is the "hash ignores the map" mutation below, which correctly changes nothing.
- **History:** an `id` (unique per table in this process), a `version`, and a log of `(version, path)` capped at `LOG_PATHS` = 65,536 paths. A page older than the log, or holding another id, gets the whole index.

**Which notes resolve again (`index.rs`).** A link's resolution is a function of its note's path, its text, and the name-map keys it reads, nothing else (`pick` and `nameless_md` only look at candidate path strings).

- `resolve` now runs through `Lookups` (`name_maps.rs`). In `watching` mode it records every key read, hit or miss. `Index::resolve`, the table, and the test oracles share that one code path, so the recorded keys are by construction exactly what resolution depends on.
- `put_node` / `take_node` (P2a's single door for file-list changes):
  - queue the changed path (`touch`);
  - when the node's map keys change (`keys_of` of the old and new node, the same definition the maps use), queue every reader of those keys (`wake`).
  - A save with the same kind of node and the same aliases changes no keys and wakes no one, so a typing save resolves only that note's own links.
- **`settle_links`** resolves the queued notes once, at the end of `upsert_note`, `remove_tree`, `relocate`, and `refresh_path`, or when the outermost `MapBatch` drops (a watcher batch settles once). It logs only notes whose entry actually changed. A re-resolve that gives an identical result touches nothing.
- **A full name-map rebuild** (scan, folder refresh, folder move, a delete of more than 256 paths, a batch over budget) resolves every note (`rebuild_links` → `refill`). It still logs only the notes whose entries differ, so a folder rename sends a delta, not the index.
- **A watcher rescan** (`Vault::finish_rescan`) hands the old table's history to the fresh index (`continue_link_history`), diffed. The page keeps patching across the swap.
- `link_index` now just copies the table. `link_sources` is unchanged.

**New command `link_changes(id, version)`** (`lib.rs`, `build.rs`, `capabilities/default.json`, `permissions/autogenerated/link_changes.toml`, CONTRACT.md):

- It returns `{ id, version, since, full, changed }`.
- `changed` maps each changed note to its whole new entry; empty lists are left out, and an empty entry means the note has no links now.
- `full` is the plain `LinkIndex` when there is no usable base.
- `link_index` stays as it was.

**Page: `src/links/linkDelta.ts` (new), behind `api.linkIndex`.**

- `linkReader` keeps the last reply's id, version, and object, asks `link_changes` since then, and patches with `patchLinks`.
- `vault.ts` and every test that stubs `api.linkIndex` are untouched.
- `patchLinks` builds a new top-level object. A map no changed note touches is shared; a touched map is copied. It never edits an object it has handed out, so nothing a consumer holds changes under it.
- Paths new to a map are inserted at their sorted place in code point order, which is the backend's UTF-8 byte order. A patched map iterates in exactly the order a full reply does. `editorHost`'s unresolved-link suggestions iterate `unresolved`, so this order is visible.
- Overlapping calls: each patches the base it asked from. The kept base moves only forward, to a higher version of the same id, or to another id from a later call.
- The browser mock (`mock/backend.ts`) answered `link_changes` with the whole index every time. Its maps are in file order, not path order, so patching them would not match its own full reply. Since review 1 it sends a delta when only lists changed (see "Review round 1").

## Tests

The brief's test is a delta compared with a full rebuild after rename, move, delete, alias, and embed edits. That is `deltas_match_a_full_rebuild_after_renames_moves_deletes_aliases_and_embeds`; it and the rest of the suite rely on these oracles.

**The oracle** (`index/link_table_tests.rs`) is the pre-P2b `link_index` and `backlinks` bodies, kept verbatim: they resolve every link of every note. `assert_links_match_walk` checks four things:

- the table equals every note resolved from scratch (targets, entries, and recorded keys);
- both reverse maps equal ones rebuilt from the table;
- `link_index` equals the walk;
- `backlinks` for every path at once equals the walk, plus each path on its own on indexes up to 2,000 files.

It also runs inside P2a's `assert_maps_match_rebuild`, so every P2a name-map test and every S4 / P2a vault batch test now checks the link table too.

A simulated page (`Page`) applies the replies as JSON would arrive. It checks that empty lists are never sent and that a delta is relative to the page's own version, then compares its copy with the walk.

**Rust tests:**

- **`deltas_match_a_full_rebuild_after_renames_moves_deletes_aliases_and_embeds`.** Three pages: one refreshed after every step, one every third step, and one new each step. Each step checks all three against the walk, and checks which notes the eager page's delta lists. The steps:
  - a typing save: no new version, empty delta;
  - a rename: `[[Target]]` goes unresolved and the alias follows;
  - a move into a folder: the relative link follows;
  - a folder move: one rebuild, a 5-note delta;
  - a delete;
  - alias add and remove;
  - embeds: `![[note]]`, `![[pic.png]]`, and `![[note#Part]]` added and removed;
  - a new note taking a name back from an alias;
  - a lower-case path clash and its delete;
  - a link rewritten to the same target through other keys, then a file taking the new key;
  - a note renamed to `.png`;
  - a 260-note bulk delete: one rebuild;
  - a watcher-shaped batch: settles once, on drop.
- **`pages_too_far_behind_or_from_another_index_get_the_whole_index`.** The same rules on a 64-path log:
  - a change larger than the log sends the whole index;
  - a page within the log still gets a delta;
  - a page behind the log's oldest path gets the whole index;
  - another index's id, or an unknown version, gets the whole index.
- **`random_link_edits_match_a_full_walk_and_pages_patch_to_it`**: 5 seeds × 250 steps over 14 link shapes (wikilinks, embeds, headings, display text, markdown links to notes and pictures, relative and partial paths, case clashes), with saves, text-only saves, renames, deletes, and batches. The eager page never needs a full reply.
- **`a_rescan_swap_continues_the_link_history`**: a real vault under `/tmp`. A file is created outside during the scan and the app saves during it. After the swap the page gets a delta of exactly the 3 notes that differ, and the index equals a rescan.
- **`a_save_at_20k_notes_updates_links_far_faster_than_a_walk`**: a ratio inside one debug run (save plus delta under 1/20 of a walk), so a loaded machine can't flake it.
- **`bench_link_deltas`** (ignored): the release numbers below.
- P2a's 5 × 300-step random sequence and its other tests now also pass the link checks.

**Page tests (`src/links/linkDelta.test.ts`):**

- `byCodePoint` agrees with UTF-8 byte order, with astral characters and U+E000–U+FFFF included.
- `patchLinks` equals the full snapshot (`JSON.stringify` and `Object.keys` order) over 5 seeds × 200 random changes with non-ASCII paths. The base is deep-frozen, so any write to it throws.
- Untouched maps are shared, and a new object is returned every time.
- `linkReader` against a fake backend:
  - one full read, then deltas only;
  - overlapping calls answered in one order and delivered in another, with changes landing between answers;
  - a switch to another id;
  - a malformed reply, which triggers a full re-read.

### P2: a popular key re-resolved in quadratic time

**The problem.** Removing an alias that N notes link to re-resolves all N. Each one detached and re-attached every membership, including unchanged ones. A removal scanned the key's reader list (N long) and shifted the target's source list. That is O(N²) under the vault write lock. The new test measured 4.9 s for 20,000 linkers in debug, against 75 ms for a full link rebuild of the same index.

**The fix** (`index/link_table.rs`):

- **`PathSet`.** Each reverse-map entry (`by_target`: target → linking notes; `readers`: key → notes that read it) is a sorted `Vec` up to 32 paths and a `BTreeSet` beyond. Adding or removing one note is a binary search plus a shift of at most 32, or a B-tree step. Both forms iterate in path order, so `backlinks` output order is unchanged. A refill pushes in path order into lists and converts the long ones once at the end (`seal_all`), so the open-time table build does not pay per-insert tree costs.
- **`relink`.** Re-resolving a note diffs its old and new targets and its old and new read keys (both sorted) and touches only the memberships that changed. A note re-resolved to the same targets moves nothing.

**The test.** `a_shared_alias_with_many_linkers_updates_in_linear_time` uses 20,000 notes, each with `[[alpha]]` and `[[alpha#Part]]`, plus a hub that has alias `alpha`. It runs four steps: remove the alias, add it back, rename the hub, delete it. Each step must:

- take under 3× a full link rebuild of the same index in the same run;
- send all 20,000 entries as a delta;
- leave a simulated page equal to a full walk;
- pass `assert_links_match_walk`.

Debug run: each step takes 117–144 ms against an 81 ms full rebuild (it was 4.9 s). `bench_link_deltas` gained the same case in release at vault size (see Measurements below).

### P3: the page did vault-sized work after a save

**No map copy per save** (`links/linkDelta.ts`). Each of the three maps in a read is now a layer: the last whole map plus the changed paths laid over it.

- The whole map is built only when something reads it: one copy, with new paths at their sorted places, the same merge as before. It is then folded into the layer. A save nobody reads the map after copies nothing.
- `linkEntryOf(links, path)` reads one note's entry without building anything.
- A pile of unread changes is folded in early once it passes an eighth of the map (and 64 paths). Carrying the pile from one read to the next therefore stays a small share of one build.
- Reads stay snapshots. A read is never changed after it is handed out; old reads keep their values whatever comes later, and each read is still a new top-level object. Its maps are enumerable getters, so `JSON.stringify`, spreads, `structuredClone`, and `toEqual` see plain data.
- Key order equals a full reply, as before.

**Which notes changed, for consumers.**

- `linkChanges(older, newer)` returns the notes whose entries may differ between two reads from one reader. It returns an empty set when nothing changed (a prose save: the backend lists the re-resolved note, but its entry is the same, so the page drops it). It returns null when that is unknown: a whole reply in between, or reads from elsewhere such as a test stub.
- `vault.linkTouch` holds that set for the last `links` refresh.
- The `links` event itself still fires at the same moments. The backlinks pane and count (excerpts), outgoing links, properties, tags, and `vaultTags` still refresh on it, so document-dependent views still update after a save that changed no link.

**Graph** (`graph/view.ts` `linksMatter`, `graph/source.ts` `readsText`). A `links` refresh is skipped when it cannot change the graph:

- **Tags shown, or a search or colour group the backend matches:** the graph reads note text, so it rebuilds as before.
- **Otherwise the graph is its files and links:** it skips a refresh that changed no entry.
- **A local graph** also skips when no changed note is in it and none of their new targets is. Such a note was out of reach before and still is.
- **A global graph** rebuilds when any entry changed.

**Base** (`bases/view.ts` `linkRefreshMatters`). A Base reads the link index only through `hasLink`; `readsOtherFiles` also lists `file.links`, `file.backlinks` and `file.embeds`. It skips a `links` refresh when no entry changed, or when it reads no links at all, unless it reads tags (re-read on each link refresh). Row data comes from the property index, which follows file mtimes and open editors, not this event, and the save's own document notice still rebuilds the Base as before.

**What still rebuilds.** A save that really changes a link still rebuilds a visible global graph (12–110 ms from 5k to 50k notes), then reheats its layout. A Base that reads links still does a full select. Patching the graph model in place, so it stays identical to a fresh `buildGraph` (node order, pair order), is its own piece. Its output order depends on every earlier note, so it needs a different model structure.

**Browser mock** (`mock/backend.ts`). `link_changes` now answers with a delta from any of the last 8 versions it served, whenever every map kept its keys in the same order (only lists changed). The patch then equals its full reply exactly, because the mock's maps are in file order, not path order. Otherwise it sends the whole index as before. The browser suites now run the delta path for ordinary saves.

### P3: the disk-event-to-page path, end to end

`link_page_tests::outside_changes_reach_the_page_as_deltas_equal_to_a_fresh_scan` (new `src/link_page_tests.rs`) works on a vault under the temp directory.

**How it runs.** Outside changes go through the watcher's own `flush_changes`. The page side is the real `linkReader` from `src/links/linkDelta.ts`, run by node through `scripts/link-page.mjs` (no new packages; node strips the types). The test answers each of the page's requests with `link_changes` serialized by `serde_json`, as Tauri does.

**The steps:**

- an app save (`write_note`) adding a link;
- an outside alias change in frontmatter;
- an outside embed edit (`![[pic.png]]` → `![[hub#Part]]`, plus `![[dir/c]]`);
- an outside prose-only edit;
- an outside rename into a new folder (one map rebuild);
- an outside replacement (a new file renamed over an existing one);
- an outside delete;

**After each settled step it checks:**

- the page's maps as JSON text equal a fresh `Index::scan`'s `link_index`, key order included;

- every read after the first was a delta, 8 of 8;
- `backlinks` for every path equals the fresh scan's, order and excerpts included;
- `assert_maps_match_rebuild`.
