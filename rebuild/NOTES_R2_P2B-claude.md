# NOTES_R2_P2B: link-index deltas

Built on `rebuild/r2-p2b-claude` from `b9fb338` (brief: `R2_P2B_TASK.md`), on top of merged P2a. This is the link half of RUST_PERF_PLAN §4.2 plus the reverse index of §4.6. Not done here: `vault-changed` carrying file entries, `changes_since` for tags and files, consumer patching (graph, Bases, Tags view), P3 (faster open), and the file tree.

## In plain words

- Before, a second after every save (and after every outside change), the page asked for the **whole** link index. Rust resolved every link of every note (24 ms at 20k notes, 74 ms at 50k), sent 3.1 MB / 7.9 MB, and the page parsed it (7.5 / 18 ms).
- Now Rust keeps every note's resolved links in memory and updates only the notes a change can affect. The page asks "what changed since version N" and gets only those notes, usually **55–300 bytes**, and patches its copy.
- The backlinks count and pane (`backlinks` for one note) read a reverse index instead of walking every note: 15 / 50 ms → **3–5 µs**.
- Nothing visible changes. The page's `vault.links` is identical to a full read, key order included, after every refresh. It is still a new object each refresh, and still refreshed at the same moments (1 s after a save, after each outside batch). Every consumer sees the same data at the same time as before.
- The cost: opening a vault builds the table once, so `scan` is about **11 % slower** (+40 ms at 20k, +110 ms at 50k), and memory is about **5 % higher** (+12 / +29 MB). The page's first link read after open gets 60 ms cheaper at 50k, so the Rust-side open total grows about 5 %. A folder rename also rebuilds the table once (see Measurements).

## How it works

**`src-tauri/src/index/link_table.rs` (new): `LinkTable`**, a field of `Index`.

- **Per note with links:** where each link points (`slots`, an index into its `outgoing` or `markdown` list), its `LinkEntry` (that note's part of `link_index`), and the name-map keys its resolution read (`reads`).
- **`by_target`:** target path → notes linking to it, sorted by path. `backlinks` reads only those notes, in the order the old full walk produced.
- **`readers`:** key → notes whose resolution read it. Keys are stored as a 64-bit FNV-1a hash of (map, key), not as strings. Two keys sharing a hash only make a change wake more notes than needed, never fewer. That is the "hash ignores the map" mutation below, which correctly changes nothing.
- **History:** an `id` (unique per table in this process), a `version`, and a log of `(version, path)` capped at `LOG_PATHS` = 65,536 paths. A page older than the log, or holding another id, gets the whole index.

**Which notes resolve again (`index.rs`).** A link's resolution is a function of its note's path, its text, and the name-map keys it reads, nothing else (`pick` and `nameless_md` only look at candidate path strings).

- `resolve` now runs through `Lookups` (`name_maps.rs`). In `watching` mode it records every key read, hit or miss. `Index::resolve`, the table, and the test oracles share that one code path, so the recorded keys are by construction exactly what resolution depends on.
- `put_node` / `take_node` (P2a's single door for file-list changes):
  - queue the changed path (`touch`);
  - when the node's map keys change (`keys_of` of the old and new node, the same definition the maps use), queue every reader of those keys (`wake`).
  - A save with the same kind of node and the same aliases changes no keys and wakes no one, so a typing save resolves only that note's own links.
- **`settle_links`** resolves the queued notes once, at the end of `upsert_note`, `remove_tree`, `relocate`, and `refresh_path`, or when the outermost `MapBatch` drops (a watcher batch settles once). It logs only notes whose entry actually changed. A re-resolve that gives an identical result touches nothing.
- **A full name-map rebuild** (scan, folder refresh, folder move, a delete of more than 256 paths, a batch over budget) resolves every note (`rebuild_links` → `refill`). It still logs only the notes whose entries differ, so a folder rename sends a delta, not the index.
- **A watcher rescan** (`Vault::finish_rescan`) hands the old table's history to the fresh index (`continue_link_history`), diffed. The page keeps patching across the swap.
- `link_index` now just copies the table. `link_sources` is unchanged.

**New command `link_changes(id, version)`** (`lib.rs`, `build.rs`, `capabilities/default.json`, `permissions/autogenerated/link_changes.toml`, CONTRACT.md):

- It returns `{ id, version, since, full, changed }`.
- `changed` maps each changed note to its whole new entry; empty lists are left out, and an empty entry means the note has no links now.
- `full` is the plain `LinkIndex` when there is no usable base.
- `link_index` stays as it was.

**Page: `src/links/linkDelta.ts` (new), behind `api.linkIndex`.**

- `linkReader` keeps the last reply's id, version, and object, asks `link_changes` since then, and patches with `patchLinks`.
- `vault.ts` and every test that stubs `api.linkIndex` are untouched.
- `patchLinks` builds a new top-level object. A map no changed note touches is shared; a touched map is copied. It never edits an object it has handed out, so nothing a consumer holds changes under it.
- Paths new to a map are inserted at their sorted place in code point order, which is the backend's UTF-8 byte order. A patched map iterates in exactly the order a full reply does. `editorHost`'s unresolved-link suggestions iterate `unresolved`, so this order is visible.
- Overlapping calls: each patches the base it asked from. The kept base moves only forward, to a higher version of the same id, or to another id from a later call.
- The browser mock (`mock/backend.ts`) answered `link_changes` with the whole index every time. Its maps are in file order, not path order, so patching them would not match its own full reply. Since review 1 it sends a delta when only lists changed (see "Review round 1").

## Tests

The brief's test is a delta compared with a full rebuild after rename, move, delete, alias, and embed edits. That is `deltas_match_a_full_rebuild_after_renames_moves_deletes_aliases_and_embeds`; it and the rest of the suite rely on these oracles.

**The oracle** (`index/link_table_tests.rs`) is the pre-P2b `link_index` and `backlinks` bodies, kept verbatim: they resolve every link of every note. `assert_links_match_walk` checks four things:

- the table equals every note resolved from scratch (targets, entries, and recorded keys);
- both reverse maps equal ones rebuilt from the table;
- `link_index` equals the walk;
- `backlinks` for every path at once equals the walk, plus each path on its own on indexes up to 2,000 files.

It also runs inside P2a's `assert_maps_match_rebuild`, so every P2a name-map test and every S4 / P2a vault batch test now checks the link table too.

A simulated page (`Page`) applies the replies as JSON would arrive. It checks that empty lists are never sent and that a delta is relative to the page's own version, then compares its copy with the walk.

**Rust tests:**

- **`deltas_match_a_full_rebuild_after_renames_moves_deletes_aliases_and_embeds`.** Three pages: one refreshed after every step, one every third step, and one new each step. Each step checks all three against the walk, and checks which notes the eager page's delta lists. The steps:
  - a typing save: no new version, empty delta;
  - a rename: `[[Target]]` goes unresolved and the alias follows;
  - a move into a folder: the relative link follows;
  - a folder move: one rebuild, a 5-note delta;
  - a delete;
  - alias add and remove;
  - embeds: `![[note]]`, `![[pic.png]]`, and `![[note#Part]]` added and removed;
  - a new note taking a name back from an alias;
  - a lower-case path clash and its delete;
  - a link rewritten to the same target through other keys, then a file taking the new key;
  - a note renamed to `.png`;
  - a 260-note bulk delete: one rebuild;
  - a watcher-shaped batch: settles once, on drop.
- **`pages_too_far_behind_or_from_another_index_get_the_whole_index`.** The same rules on a 64-path log:
  - a change larger than the log sends the whole index;
  - a page within the log still gets a delta;
  - a page behind the log's oldest path gets the whole index;
  - another index's id, or an unknown version, gets the whole index.
- **`random_link_edits_match_a_full_walk_and_pages_patch_to_it`**: 5 seeds × 250 steps over 14 link shapes (wikilinks, embeds, headings, display text, markdown links to notes and pictures, relative and partial paths, case clashes), with saves, text-only saves, renames, deletes, and batches. The eager page never needs a full reply.
- **`a_rescan_swap_continues_the_link_history`**: a real vault under `/tmp`. A file is created outside during the scan and the app saves during it. After the swap the page gets a delta of exactly the 3 notes that differ, and the index equals a rescan.
- **`a_save_at_20k_notes_updates_links_far_faster_than_a_walk`**: a ratio inside one debug run (save plus delta under 1/20 of a walk), so a loaded machine can't flake it.
- **`bench_link_deltas`** (ignored): the release numbers below.
- P2a's 5 × 300-step random sequence and its other tests now also pass the link checks.

**Page tests (`src/links/linkDelta.test.ts`):**

- `byCodePoint` agrees with UTF-8 byte order, with astral characters and U+E000–U+FFFF included.
- `patchLinks` equals the full snapshot (`JSON.stringify` and `Object.keys` order) over 5 seeds × 200 random changes with non-ASCII paths. The base is deep-frozen, so any write to it throws.
- Untouched maps are shared, and a new object is returned every time.
- `linkReader` against a fake backend:
  - one full read, then deltas only;
  - overlapping calls answered in one order and delivered in another, with changes landing between answers;
  - a switch to another id;

### P2: a popular key re-resolved in quadratic time

**The problem.** Removing an alias that N notes link to re-resolves all N. Each one detached and re-attached every membership, including unchanged ones. A removal scanned the key's reader list (N long) and shifted the target's source list. That is O(N²) under the vault write lock. The new test measured 4.9 s for 20,000 linkers in debug, against 75 ms for a full link rebuild of the same index.

**The fix** (`index/link_table.rs`):

- **`PathSet`.** Each reverse-map entry (`by_target`: target → linking notes; `readers`: key → notes that read it) is a sorted `Vec` up to 32 paths and a `BTreeSet` beyond. Adding or removing one note is a binary search plus a shift of at most 32, or a B-tree step. Both forms iterate in path order, so `backlinks` output order is unchanged. A refill pushes in path order into lists and converts the long ones once at the end (`seal_all`), so the open-time table build does not pay per-insert tree costs.
- **`relink`.** Re-resolving a note diffs its old and new targets and its old and new read keys (both sorted) and touches only the memberships that changed. A note re-resolved to the same targets moves nothing.

**The test.** `a_shared_alias_with_many_linkers_updates_in_linear_time` uses 20,000 notes, each with `[[alpha]]` and `[[alpha#Part]]`, plus a hub that has alias `alpha`. It runs four steps: remove the alias, add it back, rename the hub, delete it. Each step must:

- take under 3× a full link rebuild of the same index in the same run;
- send all 20,000 entries as a delta;
- leave a simulated page equal to a full walk;
- pass `assert_links_match_walk`.

Debug run: each step takes 117–144 ms against an 81 ms full rebuild (it was 4.9 s). `bench_link_deltas` gained the same case in release at vault size (see Measurements below).

### P3: the page did vault-sized work after a save

**No map copy per save** (`links/linkDelta.ts`). Each of the three maps in a read is now a layer: the last whole map plus the changed paths laid over it.

- The whole map is built only when something reads it: one copy, with new paths at their sorted places, the same merge as before. It is then folded into the layer. A save nobody reads the map after copies nothing.
- `linkEntryOf(links, path)` reads one note's entry without building anything.
- A pile of unread changes is folded in early once it passes an eighth of the map (and 64 paths). Carrying the pile from one read to the next therefore stays a small share of one build.
- Reads stay snapshots. A read is never changed after it is handed out; old reads keep their values whatever comes later, and each read is still a new top-level object. Its maps are enumerable getters, so `JSON.stringify`, spreads, `structuredClone`, and `toEqual` see plain data.
- Key order equals a full reply, as before.

**Which notes changed, for consumers.**

- `linkChanges(older, newer)` returns the notes whose entries may differ between two reads from one reader. It returns an empty set when nothing changed (a prose save: the backend lists the re-resolved note, but its entry is the same, so the page drops it). It returns null when that is unknown: a whole reply in between, or reads from elsewhere such as a test stub.
- `vault.linkTouch` holds that set for the last `links` refresh.
- The `links` event itself still fires at the same moments. The backlinks pane and count (excerpts), outgoing links, properties, tags, and `vaultTags` still refresh on it, so document-dependent views still update after a save that changed no link.

**Graph** (`graph/view.ts` `linksMatter`, `graph/source.ts` `readsText`). A `links` refresh is skipped when it cannot change the graph:

- **Tags shown, or a search or colour group the backend matches:** the graph reads note text, so it rebuilds as before.
- **Otherwise the graph is its files and links:** it skips a refresh that changed no entry.
- **A local graph** also skips when no changed note is in it and none of their new targets is. Such a note was out of reach before and still is.
- **A global graph** rebuilds when any entry changed.

**Base** (`bases/view.ts` `linkRefreshMatters`). A Base reads the link index only through `hasLink`; `readsOtherFiles` also lists `file.links`, `file.backlinks` and `file.embeds`. It skips a `links` refresh when no entry changed, or when it reads no links at all, unless it reads tags (re-read on each link refresh). Row data comes from the property index, which follows file mtimes and open editors, not this event, and the save's own document notice still rebuilds the Base as before.

**What still rebuilds.** A save that really changes a link still rebuilds a visible global graph (12–110 ms from 5k to 50k notes), then reheats its layout. A Base that reads links still does a full select. Patching the graph model in place, so it stays identical to a fresh `buildGraph` (node order, pair order), is its own piece. Its output order depends on every earlier note, so it needs a different model structure.

**Browser mock** (`mock/backend.ts`). `link_changes` now answers with a delta from any of the last 8 versions it served, whenever every map kept its keys in the same order (only lists changed). The patch then equals its full reply exactly, because the mock's maps are in file order, not path order. Otherwise it sends the whole index as before. The browser suites now run the delta path for ordinary saves.

### P3: the disk-event-to-page path, end to end

`link_page_tests::outside_changes_reach_the_page_as_deltas_equal_to_a_fresh_scan` (new `src/link_page_tests.rs`) works on a vault under the temp directory.

The page side is the real `linkReader` from `src/links/linkDelta.ts`, run by node through `scripts/link-page.mjs` (no new packages; node strips the types). The test answers each of the page's requests with `link_changes` serialized by `serde_json`, as Tauri does.

**The steps:**

- an app save (`write_note`) adding a link;
- an outside alias change in frontmatter;
- an outside embed edit (`![[pic.png]]` → `![[hub#Part]]`, plus `![[dir/c]]`);
- an outside prose-only edit;
- an outside rename into a new folder (one map rebuild);
- an outside replacement (a new file renamed over an existing one);

- `backlinks` for every path equals the fresh scan's, order and excerpts included;

### P2: link settling and reply construction could still hold up queued saves

**The problem.** Round 2 resolved queued notes under the write lock in 2 ms slices. The deadline was checked only every 32 notes, so a slice of link-heavy notes ran long. The first lookup of a large ambiguous key built its whole candidate index inside the lock, again in every slice. Waking a key copied all of its readers into the queue inside the save. Replies cloned and collected every entry under the read lock, which blocks a writer as surely as the write lock.

**The fix.** Nothing vault-sized runs under the lock any more: not in a save, not while settling, not while building a reply.

- **A save queues keys, not readers** (`link_table.rs`).
  - `wake` records the changed key. `expand` later queues its readers in bounded steps, in path order from a cursor.
  - A reader that leaves the key, or joins it, meanwhile was itself resolved against the new owners, so a moving reader set misses nobody. Waking a key again restarts its cursor.
- **Inline work is bounded in links too** (`index.rs`). The app settles a change before the write returns only when it wakes at most `INLINE_LINKS` (256) notes holding at most `INLINE_LINK_WORK` (2,048) links. Forty notes of 3,000 links are now deferred; round 2 resolved them inside the save.
- **A name with many files keeps its picks** (`name_maps.rs` `NamePicks`). For a name with 16 or more files, the maps keep:
  - the best note and the best other file, by (length, path);
  - each folder's files with that name.

  They are updated with the name's list on every add and remove, so `[[README]]` among 25,000 READMEs is a few lookups, under the lock or not, and nothing is built per batch. This replaces round 2's `PickIndex`/`PickCache`.
- **Resolution runs off the lock** (`index/link_jobs.rs`, driven by `link_reads::settle`). Each job has five steps, and only two hold a lock briefly:
  1. Under the write lock, `link_job` takes up to 128 queued notes or 1,024 links as shared `Arc` nodes, with an `EditMark`.
  2. Off the lock, `ask` resolves each note against nothing. A resolution that misses every lookup takes every branch, so this lists every map key the note could read.
  3. Under the read lock, `answer` looks those keys up, 2,048 per hold.
  4. Off the lock, `finish` resolves each note from the answers.
  5. Under the write lock, `publish` stores each note, unless its node changed since the mark or a key it asked about gained or lost an owner (the new per-index edit log: `Edit::Node`, `Edit::Key`). Such a note stays queued. A full map rebuild (a new epoch) drops the whole job.

  A key's answer depends only on that key's owners and the asking note's folder. A stored note therefore equals the note resolved against the maps at publish: what an inline settle would have stored. Typing in another note touches neither, so jobs finish while saves keep coming. A first version checked a single generation number; with a save every millisecond in the latency test, no job ever published.

### P2: a stepped backlink reply could mix two resolutions of one link

**The problem.** Take a note S with `[[A]]`, `[[B]]` and `[[X]]`, where X is an alias of A. A `backlinks` reply for A and B copies S for A, then X moves from A to B, then the reply copies S for B. S's entry stays `[A, B]`, so the table's version doesn't move, and S's text doesn't change. Round 3's reply checked only those two, so it listed the `[[X]]` line under both targets, which no full rebuild gives.

**The fix** (`index.rs`, `index/link_replies.rs`, `index/link_jobs.rs`):

- **A new edit kind.** Every replacement that changes a note's resolved links logs `Edit::Entry(path)`, the slots alone included (`Replaced::{Same, Slots, Entry}`). Node edits were logged already.
- **The reply patches instead of restarting.**
  - It copies sources in steps as before, from a mark taken once the table is settled.
  - At a settled check it reads the node and entry edits since the mark (`Index::edited_paths`, in steps) and copies each of those notes again, now. For every target it drops that note's old copy and adds the new one if it still links there.
  - It repeats until a settled check finds no newer edit. Every note then is either one no edit touched since the mark, copied once in path order, or one copied again after its last edit, so the reply equals the settled table at that check.
- **Starting over.** The reply starts over only when the edits since its mark are unknown. That happens after a full map rebuild (a new edit epoch), when a rescan's fresh index takes over (a new epoch, so this covers rescans), or after more edits than the log keeps (raised to 65,536). The new copy is still taken in bounded steps.
- **Copying without settling.** Copy steps no longer require a settled table: an unsettled note is edited after the mark, so it is patched later. A copy step now advances past listed paths that turn out not to link (see the next finding) by the paths it read, not the sources it kept.

**Tests:**

- `a_backlink_reply_across_an_alias_move_lists_each_line_once` is the reviewer's case. B takes the alias, then A gives it up, between two copy steps; the table's version is checked unchanged. The reply lists S's three lines once each, the alias line under B, and equals the walk.
- `a_backlink_reply_across_a_rescan_swap_starts_over`: a reply begun on one index finishes on a fresh one, as after a rescan, and equals the fresh one.
- `stepped_replies_equal_replies_made_at_once` still passes: random backlink replies with edits and settling between steps, each against the walk at the moment it finishes.

### P2: one link-heavy note could hold the write lock for quadratic work at publish

**The problem.** A job admits a whole note even when it holds far more links than the job's budget. Its resolution ran off the lock, but `publish` then rebuilt the old and new target sets under the write lock. That scanned `outgoing` for every Markdown target (`Resolved::targets`), which is quadratic. It then applied every membership change in one hold.

**The fix** (`index/link_table.rs`, `index/link_jobs.rs`):

- **Sorted targets, kept per entry.** Each entry keeps its targets once each, sorted (`Resolved::members`, places in `outgoing` then `markdown`). They are sorted when the note is resolved, which for a job is off the lock. The quadratic scan is gone, including from the full rebuild's `link`.
- **The membership diff is worked out off the lock.** `LinkJob::finish` takes the entry captured at `link_job` and computes `Moves`, a merge of the two sorted target lists and the two sorted read lists, along with whether anything changed at all.
- **Checked before it is applied.** `publish` stores a note only if, since the mark, its node and the keys it asked about are unchanged (as before), and its current entry is the very one the diff started from (`Arc::ptr_eq`). Otherwise the note stays queued.
- **At most `MEMBER_STEP` (2,048) membership changes per hold.**
  - A note with more is put in over several holds: its new memberships first, then its entry, then its old memberships. `publish` returns `More`, and `link_reads::settle` lets waiting writers in before each call.
  - Between holds the reverse maps can list a note for a target or key its entry lacks, never the other way round. A reader of a key is resolved again for nothing, and a backlink source that doesn't link there has no lines (`backlink_sources` filters it out).
  - Each hold re-checks the note. If it changed meanwhile, what was added goes on the cleanup queue (`LinkTable::forget`), and the note stays queued.
- **Old memberships are cleared in steps.**
  - **When cleared.** A long old entry's memberships are queued (`Stale`) rather than removed at once, after a job's publish or an inline replacement, for instance deleting the note. `link_job` clears up to 4,096 of them per job.
  - **The check.** Each is checked against the note's entry at that moment and removed only if the entry lacks it, a binary search in its sorted lists. A note being staged is left alone until its entry is in.
  - **Inline saves.** So a save that deletes a 40,000-link note queues its memberships and returns.
- **Tests account for staging.** `reverse_maps_match` compares the table with the live maps after clearing the queue on a copy. A full map rebuild empties the queue.

### P2: Bases could reorder rows, first paint included, for a mixed-kind sort column

**The problem.** In round 3 every `select` used the stepped merge sort. That equals `Array.prototype.sort` only when the comparison is consistent. A column mixing kinds compares number pairs as numbers and other pairs as text, which can go round in a cycle (-2 < "-3" < -10 < -2), and there the two sorts differ. **The fix** (`bases/model.ts`). `orderedWork` checks each sort column, in steps, for a comparison that is a total preorder over these rows:

- only dates, all parsed or none parsed;

Then every stable sort gives the same order, the native one, and the stepped merge sort runs. Otherwise the rows are sorted by `Array.prototype.sort` itself with the same comparator, on the same input order, in one task, as before round 3. Empties and the name/path tie-break are consistent either way. This is exact on any engine, the app's WebKit included, since it never guesses the engine's algorithm.

- **The key scan.** Round 4's staged publish validated a note in every hold by walking all of the note's queried keys against the set of key edits since the job's mark. That is O(K) per hold and about O(K² / MEMBER_STEP) across the publish, for a note with K distinct queries.
- **The edit read.** The first hold also took in every edit logged since the mark at once, up to 65,536.

**The fix** (`index/link_jobs.rs`, `index.rs`):

- **Lookup maps built off the lock.** A job now builds its own maps from key and path to note. `ask` builds the key map off the lock, and `link_job` builds the path map from its at most 128 notes.
- **Bounded edit reads.** `publish` reads the edits since the last mark it checked at most `EDIT_STEP` (4,096) per hold, using a new `Index::edits_after(mark, n)`.
  - Each edit is looked up in the maps. It marks the notes it names `changed` and leaves the maps, so a key is marked once at most.
  - While unread edits remain, `publish` returns `More` without storing anything. A note is only stored once every edit up to that hold has been checked.
  - The entry identity check (`Arc::ptr_eq` against the entry taken at the start) stays as it was.
  - If edits come faster than one step a hold for long enough, the log overflows. The job is then dropped as before (`Stale`), and its notes stay queued.
- **The readers map in 64 parts** (`index/link_table.rs`, `Readers`). Measuring the fix showed one more cost proportional to the vault in a hold: a note bringing tens of thousands of new keys made the reverse readers map double, rehashing every key in one hold.
  - Debug, 96,000 links: 3.4 → 6.7 → 7.9 ms holds at the doublings to 57k, 115k and 229k slots.
  - The map is now split by key-hash bits 32–37. Those bits are unused by the maps' own bucket index (low bits) and tag (top 7 bits), so each growth rehashes a 64th of the keys.
- **Cleanup changes.**
  - The cleanup step is now `MEMBER_STEP` (2,048), down from 4,096, so a cleanup hold does no more than a publish hold.
  - Old entries the cleanup is done with are handed to the job and dropped with it, off the lock.

**Tests:**

### P3: a pointer move during a stepped tick changed its inputs

**The problem.** A drag wrote the dragged node's position straight into the simulation's arrays, possibly between a tick's steps. A tick whose quadtree already held the old position then read the new one in its repulsion pass. That gives forces neither whole tick would.

**The fix** (`graph/sim.ts`, `graph/view.ts`):

- **`Simulation.place(i, x, y)`.** Between ticks it moves the node at once. During a tick it records the place, and the tick's last step puts the node there after integrating.
- **The tick's inputs stay fixed.** Every position the tick reads is the one it began with. The result is a whole tick with the move at its end boundary.
  - Fixing the node mid-tick only matters at integration, where it acts as if it was set at the start.
  - Dropping a node mid-tick likewise acts as if it was dropped before the tick, since forces don't read `fixed`.
- **What's drawn.** `draw` and `nodeAt` run inside `sim.showing(...)`. It swaps the placed positions in and back out, between the tick's steps (never during one, since JavaScript runs one thing at a time). The dragged node is therefore drawn and hit where the pointer put it, with no lag.

**Test:** `a drag during a tick in steps lands at the tick's end, as between whole ticks` (`graph.test.ts`), with 5,000 nodes and 4,500 links.

### P2: a pending set of woken keys made unrelated saves walk all of them

**The problem.** A frontmatter edit can wake tens of thousands of aliases that one long note reads.

- **The estimate.** Until the woken keys drained, every later save, even typing elsewhere, ran `queued_work`. That summed the readers of every woken key, even when the threshold was crossed at the first one.
- **The expansion.** `expand` charged its budget only for readers it queued, so a woken key with no readers left cost nothing, and one expansion could walk any number of them.
- **Finding the next key.** The woken keys were a hash map, and `expand` took the first key each time. In a hash map that means scanning past every bucket emptied before it.

**The fix** (`index/link_table.rs`, `index.rs`).

- **The estimate stops at the threshold.** `queued_work` became `queued_over(n)`, which returns once more than `n` notes are counted. Each woken key counts as at least one.
- **The expansion charges every key it looks at.** A key costs at least one against the budget, so a key with no readers left uses budget too, and any key left over waits for the next step.
- **The woken keys are ordered** (a `BTreeMap`), so taking the first one costs nothing extra.
- **What a save still does when the estimate passes.** It still expands what remains inline, as before; that is at most `n` keys and `n` readers. So a save looks at no more than about twice the threshold.

**Test: `saves_and_jobs_behind_many_woken_keys_look_at_a_bounded_number_of_them`** (unit test, with a new counter of woken keys looked at, `take_keys_seen`).

- **Jobs.** The long note is then deleted. One settle step resolves it, and its 6,000 memberships go to staged cleanup, so the first job's cleanup leaves keys ahead of the expansion with no reader.

**The fix** (`index/link_table.rs`, `index.rs`, `index/link_jobs.rs`, `index/file_map.rs`):

- **The write only marks the walk.** The name maps are still rebuilt under the lock, as required. Then `requeue` sets a `Sweep` (the walk's start) in constant work. A later bulk change resets it, so the walk starts over.
- **The walk runs in steps.** `LinkTable::sweep(budget, files)` queues the next notes, a step at a time, in path order:
  1. the table's old entries;
  2. then the files with links that have no entry yet. Nodes from the bulk change itself queue nothing (`put_node` skips while the maps are dirty), so this second pass is needed.
- **Where it runs.** `link_job` sweeps before it expands woken keys (budget `EXPAND_STEP`), and `settle_links_until` does too (`SETTLE_STEP`).
- **The queue stays small.** Each step looks at no more than its budget, less the notes already queued, so the queue stays near one step instead of growing to the vault.
- **Pending and saves.** The walk counts as pending (`has_pending`). While it runs, the inline estimate (`queued_over`) says "too much" at once, so a save during the walk leaves the work to the jobs.
- **Why the walk misses nothing.**
  - An entry stored meanwhile was resolved against the current maps, by a job begun after the rebuild. Jobs begun before it are dropped, since `edits.restart()` starts a new epoch.
  - A note added or changed meanwhile was queued by its own change.
  - A later bulk change starts the walk over, since notes already passed may read keys it moved.
- **A file walk from a cursor.** `Files::after(path)` walks the file list from a point (the `BTreeMap` range). `Files::iter` now uses the same range type.

**Tests:**

- **`a_bulk_change_queues_every_note_for_jobs_and_settles_to_a_full_walk`** (unit test, small steps) now also checks:
  - the folder move swept nothing and queued no note itself;
  - no job step swept more than its budget;
  - the queue never held more than 8 notes.
- **The second bulk change in that test now comes later.** The folder delete happens at job 200, once the walk has passed `l/0.md`, which reads `g/n0.md`. Without the restart, `l/0.md` keeps its `g/` link, and the final full-walk comparison fails on it.
- **`queued_saves_of`, used by every latency test in `link_page_tests.rs`, now queues one save on the lock before the write lets go of it.**
  - The test holds the guard, starts a thread that asks for the lock, gives it 5 ms to block, then runs the write.
  - It asserts:
    - the write swept nothing (`Index::take_swept`);
    - the queued save waited no longer than the write, plus its 5 ms head start, plus a quarter of the settle;
    - the time from release to that save being done counts in the worst-save bound.

### P3: a large pending queue left its capacity to later saves

**The problem.** The pending set was a `HashSet`. Once it had grown to vault size and been drained, taking the first few notes from it scanned every bucket the drain had left empty. Both `take_some` and `link_job`'s walk over `pending()` did this, under the write lock.

**The fix:**

- The pending set is a `BTreeSet<Arc<str>>`, and `take_some` uses `pop_first`. Taking the first entries follows the queued items, and draining frees nodes as it goes.
- The new walk also keeps the queue near one step during a bulk change.

**Test:** `a_queue_drained_after_a_large_bulk_update_is_quick_to_take_from` (unit).

- 200,000 notes are queued, as a round-6 bulk change did, and all but one are taken off.
- Then 2,000 rounds each queue one note, look at the first and take two.
- They take 1.4 ms in debug. With the hash set put back they take 462 ms, over the test's 40 ms bound.

### P3: a cancelled graph build kept the refresh debounce live on irrelevant events

**The problem.** Since round 6, `scheduleRebuild` cancels a build under way by bumping `seq`. The cancelled build then returned at its next slice without clearing `building`. Until another build finished, `linksMatter` treated every link change as relevant. Each one, even for a note the graph cannot show, reset the 200 ms refresh timer, so a steady stream of them kept the local graph stale.

**The fix** (`graph/view.ts`):

- `building` now holds the `seq` of the build under way (0 for none).
- `scheduleRebuild` clears it when it cancels that build.
- The end of a build clears it only if it is still that build's own (`building === mine`), so an older one stopping never clears a newer one's. Every await in `rebuild` is followed by a `seq` check, so today an older build never reaches that line anyway. The guard is checked by inspection only.

**Test:** `scripts/test-link-refresh-guards.mjs` part 6 (in `npm test`).

- **The cancel.** The local graph of P3 has its rebuild for P3 → Q3 held, using the dev-only hold from round 6. Q3 then gains `[[R3]]`. That change cancels the held build, and a listener ends the hold in the same change.
- **The stream.** For 1.5 s, X3.md (outside the graph) gains a new link every 60 ms, and the link index is refreshed after each.
- **The check.** The graph must show the 7 nodes of the new build by the end of the stream.
- **Without the fix,** I ran it against the unfixed code first: it stays at 3 nodes ("3 !== 7"). With the fix it passes, with 25 irrelevant changes in the stream.
