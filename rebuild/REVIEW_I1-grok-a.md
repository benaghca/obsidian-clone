## Scope

Linux clipboard reads go through `std::process::Command` only (`rebuild/app/src-tauri/src/clipboard.rs`). There is no shell, no new crate, and no network. `Cargo.toml` and `package.json` are unchanged. Cinder's `src/clipboard.rs` was read and not edited.

Wayland (`WAYLAND_DISPLAY` set) runs `wl-paste --list-types`, then `wl-paste --no-newline --type <mime>`. Otherwise X11 runs `xclip -selection clipboard -t TARGETS -o`, then `xclip -selection clipboard -o -t <mime>`. The mime is the first exact line among `image/png`, `image/jpeg`, `image/webp`, `image/gif`, `image/bmp`, with PNG winning when both PNG and JPEG are offered. The argument is that fixed string. A missing tool is `install wl-clipboard to paste images` or `install xclip to paste images`. Any other failure to start the tool is `{program}: {error}`. No image is JSON `null`. An image is the mime, one `\n`, then the bytes. The read stops at 20 MB (`too large to paste`) and does not return those bytes. A type list over 64 KB is `clipboard type list is too large`. macOS and Windows return `null`.

`write_file_bytes` is `#[tauri::command(async)]` and takes `tauri::ipc::Request`. The body is raw bytes. The vault-relative path is the `x-grove-path` header, percent-encoded (`/` and `A-Za-z0-9-._~` left as themselves, other bytes as uppercase `%HH`, space as `%20`). A JSON body is `write_file_bytes expects a raw body, not JSON`. The vault checks, the 20 MB cap, the no-overwrite rule, and the `vault-changed` create to other windows are unchanged. `rebuild/CONTRACT.md` describes both commands.

`read_clipboard_image` is in `generate_handler!`, `build.rs`, `capabilities/default.json` (`allow-read-clipboard-image`), `permissions/autogenerated/read_clipboard_image.toml`, and the generated ACL manifest. `every_command_is_in_build_manifest_and_default_capability` passed.

The 10 MB bench `write_10mb_stays_off_the_calling_thread` passed. `write_10mb_ms=4.2`. The file was 10,485,760 bytes under `/tmp`. The writer thread was not the caller. Both `write_file_bytes` and `read_clipboard_image` carry `#[tauri::command(async)]`, which Tauri runs inside `async_runtime::spawn`, off the thread that received the IPC.

## Small fix on this branch

`src/api.ts` still sent `{ path, bytes: number[] }`. The new command rejects that body, so today's file paste and file drop (`saveAttachments` → `api.writeFileBytes`) would fail in the desktop app. I2 owns `read_clipboard_image` in the paste handler and the canvas image card. It does not own the write path that already saves dropped and pasted files.

`writeFileBytes` in the desktop app now passes the `Uint8Array` as the invoke body and the path in `x-grove-path`, matching the contract. The browser mock still takes `{ path, bytes: number[] }`, so the existing vitest and browser scripts keep that path. `CONTRACT.md` now says so.

`encode_grove_path` and `split_packed` were unused in the library build (the page encodes the path and splits the clipboard body). Both are `#[cfg(test)]` now. The lib build is quiet.

## Limits, already in the builder's notes

A clipboard owner that never answers blocks one async worker until the tool exits. There is no timeout. It does not run on the GTK thread. The postMessage IPC fallback cannot send a raw body; Linux WebKit uses the custom protocol, which sends the `Uint8Array` as the request body. Screenshot paste through `read_clipboard_image` is still I2.

No GUI window was opened. The desktop invoke shape was checked against Tauri 2.12 (`Uint8Array` as `application/octet-stream`, custom headers on `Request`). The browser suite exercises the mock branch.
