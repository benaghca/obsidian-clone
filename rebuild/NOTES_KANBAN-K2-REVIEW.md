# Review: Kanban K2 (Codex), the safe property edit

Branch `rebuild/k2-review-claude`, from `rebuild/kanban-k2-codex` (`5df2936`). Codex's branch is unchanged. Git ran with `-c core.hooksPath=/dev/null` throughout, and no hook scripts were run. Nothing was pushed.

VERDICT: OK

That verdict holds with the two fixes below, which are committed on this branch (`645edd7`, `bfcc05f`, `ec8777a`). K2 is correct, in scope and fast. The two fixes were:

- the folder fsync on every save, a main-thread regression on a real disk;
- the open-time sweep, which could delete files that weren't Grove's.

Merge this branch, not `rebuild/kanban-k2-codex` alone.

## In plain words

- **The write itself is right.**
  - Rust and TypeScript give byte-identical results on Codex's 100 corpus cases, and on 40,000 random cases I generated:
    - random frontmatters with BOM, CRLF, quotes, flow and block lists, comments, duplicates and nested YAML;
    - random edits, with stale expectations mixed in.
  - Only the edited property's lines change.
  - A stale expectation is refused, and a dry run writes nothing.
- **Two problems, both fixed here:**
  1. **Saves got slower on a real disk.** K2 added a folder fsync to `atomic_write`, which every note save uses. Saves run on the GTK main thread. On Chris's btrfs `/home`, a save went from about 4 ms to about 9 ms median, with peaks over a frame (22 ms). Codex measured only on `/tmp`, which is in RAM, so it never showed. Now only `set_property`, which runs off the main thread, syncs the folder; saves are back to their old cost.
  2. **The open-time temp sweep deleted any file ending in `.grove-tmp`,** not only Grove's own temps. It now removes only `atomic_write`'s exact name format, `.{name}.{pid}.{nanos}.grove-tmp`, from a process that is no longer running.
- **Performance is otherwise level or better.** The Rust index got faster (scan 113 → 73–81 ms at 5,000 notes). P6 holds:
  - on `/tmp`: 0.063 ms (10 KB) and 3.1 ms (1 MB);
  - on the real disk: about 2.6 ms of work for 1 MB, plus 7–15 ms of fsync wall time, off the main thread.

## What I checked, and how

1. **Byte parity, Rust against TS.**
   - Codex's corpus: `cargo test` and vitest both pass.
   - **My differential fuzz:**
     - A scratch generator (`scratchpad/k2r/fuzz.mjs`, not committed) made two corpora of 20,000 cases each: random frontmatters from 40 line shapes, 27 keys and 29 tricky values (quotes, `: `, `#`, leading `-`, `[x]`, `{y}`, multi-line, tabs, emoji, `null`, `~`, dates).
     - Every case was run through the TS `editProperty`, and its output became the expected value. Each corpus was then swapped in for `property-edits.json` (the original backed up and restored after), and `cargo test corpus` was run.
     - **Rust matched TS on all 40,000 cases:** status, `before`, `after`, `current`, `reason`, and the full output text. The mix was 11,790 `done`, 4,894 `unchanged`, 1,629 `conflict` and 21,687 `refused`.
2. **Bytes outside the property never change.**
   - The splice copies the prefix and suffix of the original string. The new lines keep each original line's own ending, and new lines use the opening fence's ending.
   - Both engines then parse the result again and refuse unless every other property's key and lines and the body bytes are identical, and the property reads back as intended.
   - The fuzz output texts agree byte for byte between two independent engines.
   - `props.rs`'s rewritten reader keeps the old cap and close rules. One deliberate change: an unclosed frontmatter is now an error ("not safely editable") instead of "no frontmatter", so an edit can't put a second `---` block above it. That is right.
3. **The compare-and-swap.**
   - `before == after` comes first, so retries and double drops are `unchanged`. Otherwise, lines that differ from `expect` give `conflict`, and nothing is written.
   - Freshness: the note is stat'ed before the read, after the read, and again just before the write (size, mtime, and on Unix dev/inode/ctime). On a change it retries up to three times, then returns `conflict`.
   - Rust tests cover an external write during the read (with a test hook), conflict and unchanged, and invalid paths, bytes and sizes. The fuzz included 1,629 stale expectations.
4. **`dry_run` never writes.** The Rust test checks that the bytes are unchanged, the metadata is the same (`same_file`), the index is unchanged and no own-write is marked. `lib.rs` emits no event for a dry run, and the mock leaves the file alone.
5. **`atomic_write` gives old or new bytes, never partial, and keeps the mode.**
   - It writes a temp file in the same folder (`create_new`), syncs it, copies the old file's mode first, then renames.
   - On error it removes only its own temp; a failed rename onto a folder leaves the destination untouched (Codex's test).
   - I added a test that both the plain and the durable write keep mode `0640` and leave no temp. Codex's `set_property` test covers the mode through the command, plus a refused symlink.
   - Hard links, xattrs and ownership are still not kept (approved R6).
6. **The sweep removes only Grove's own temp files inside the vault.**
   - It walks from the vault root without following symlinks, and skips `.obsidian`, `.git` and `.trash`.
   - **It matched any `*.grove-tmp` file. Fixed.** It now takes only `temp_path_for`'s exact format, with a digits-only PID and nanoseconds: `.{name}.{pid}.{nanos}.grove-tmp`. Grove's settings saves use the same function, so their temps match too.
   - Live PIDs are kept (this process, and on Linux any `/proc/<pid>`).
   - The test now uses a real dead-process temp (PID `u32::MAX`) and checks that five look-alikes survive: `keep.grove-tmp.md`, `notes.grove-tmp`, `.x.grove-tmp`, `.a.1.x.grove-tmp` and `.a.+1.2.grove-tmp`.
7. **The lock and the thread.** `set_property` is `#[tauri::command(async)]`, so it is off the GTK thread. It holds the vault mutex for the read, compare, write and index update, as planned.

The plan (KANBAN_PLAN §4.3 step 10) had said to sync the folder "for every `atomic_write` caller". That plan was mine, and it didn't account for saves running on the main thread. The durability point (a rename surviving a power loss) matters most for the board's moves, which have no editor holding the text. Editor saves keep the old guarantee: the file data is synced before the rename, and the next autosave rewrites anyway.

## Notes for later pieces (not blockers)

- **K5/K6:**
  - A `set_property` holds the vault lock for 7–15 ms on a real disk. Reads queued behind it (a Bases rebuild's `properties`, search) wait that long; none of them run on the GTK thread.
  - Paint optimistically (as the plan says), and don't wait for the result before the next frame.
- **K7:**
  - Run the crash-injection and racer tests on a real filesystem, not `/tmp` (tmpfs makes fsync free and hides ordering).
  - Reuse my fuzz approach (TS output as the Rust corpus).
- **Codex's test lines** in `edit.rs` aren't rustfmt-clean (the long `assert!`s). Cosmetic; I left them as they are.
- **The sweep on non-Linux Unix and Windows** can't tell if another Grove process is alive, so another running instance's in-flight temp could be removed at open. That is rare (two Grove instances on one vault, at the same moment). On Linux it uses `/proc`.
